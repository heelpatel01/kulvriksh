## 2. What was built

### Part A: public services
- `/services` reads active services from the API, revalidating every 60 s with the tag `public-services`.
- Admin changes expire the tag immediately (`updateTag`).
- It has a loading skeleton, an empty state and an unavailable state with "Try again". If the API fails after a good render, the error boundary keeps the last good page.

### API (`apps/api/src/auth/`)
- **Endpoints** (customer routes check the session on every request):

  | Endpoint | Behaviour |
  |---|---|
  | `POST /api/v1/auth/otp/request` | 202 with the same body for every number |
  | `POST /api/v1/auth/otp/verify` | Returns the session token to the Next.js server only |
  | `GET /api/v1/auth/session` | Session check |
  | `POST /api/v1/auth/logout` | Idempotent, returns 204 |
  | `POST /api/v1/auth/logout-all` | Ends every session of the customer |
  | `GET /api/v1/me` | Customer route |

- **Codes:**
  - generated by the CSPRNG (`crypto.randomInt`)
  - stored only as `HMAC-SHA-256(OTP_HMAC_KEY, challenge id ‖ code)`
  - compared in constant time
- **Order of checks follows F-AUTH-02:** lockout → atomic attempt increment *before* the comparison → compare → atomic consume and session creation in one transaction.
- **Failure budget:** wrong codes count per number across challenges, so a new code does not reset it. Reaching the limit applies a lockout that `greatest()` never shortens.
- **Rate limits:** fixed-window atomic upserts per number and per IP, for both requests and verifications. Bucket keys are HMACs (separate `RATE_LIMIT_HMAC_KEY`), so no raw number or IP is stored. Responses are 429 with `Retry-After`.
- **Resend:** a cooldown applies, and a resend invalidates the earlier code.
- **Generic responses:** registered and unregistered numbers get an identical status and body.
- **Delivery failure:** returns a retryable 503, invalidates the challenge and logs an alertable error.
- **Sessions:**
  - a 256-bit random token; only its SHA-256 is stored
  - absolute and idle expiry
  - `last_seen_at` written at most every 5 minutes
  - expired or deactivated sessions are revoked when next seen
  - a deactivated account cannot sign in
- **Fail-closed:** an unreachable database gives 503. Raw-query driver errors (P2010 with an adapter kind) are now classified as well.
- **Development outbox:**
  - keeps codes in process memory only
  - its route is registered only with `OTP_DELIVERY=development`, which the config refuses unless `NODE_ENV=development`, and it also requires the admin preview token
  - never logs codes
- **Proxy trust:** `trust proxy` is limited to loopback, so only the local Next.js server can supply the client IP.

### Web (`apps/web`)
- **`/sign-in`:** a real two-step form using Server Actions.
  - The resend button counts down the cooldown.
  - Errors are announced with `role="alert"`.
  - In development only, a "Development inbox" box shows the code.
  - A signed-in visitor is redirected to `/dashboard`.
- **Session cookie:**
  - production: `__Host-kv_session`, with HttpOnly, Secure, SameSite=Lax and Path=/
  - development: `kv_session`, without Secure
  - The token goes only from the cookie to the Next.js server, then to the API as a Bearer header.
  - When a new session is created, the previous one is revoked.
- **Route protection:**
  - `proxy.ts` redirects requests without a cookie to `/sign-in?next=…`.
  - The layout and every dashboard page validate the session with the API, because layouts do not re-render on client navigation.
  - Return paths are restricted to `/dashboard…`, which prevents open redirects.
- **Sign-out:**
  - Sign-out in the shell revokes the session, clears the cookie and does a full-document navigation.
  - The settings page has "Sign out of all devices".

## 3. Provisional settings (FQ-1 to FQ-4; each is one environment variable, see `apps/api/.env.example`)

| Setting | Default | Assumption |
|---|---|---|
| OTP length | 6 | Common for SMS codes |
| OTP lifetime | 300 s | Short expiry |
| Resend cooldown | 60 s | |
| Wrong attempts per code | 5 | |
| Wrong attempts per number before lockout | 10 per hour | Lockout 30 min |
| Code requests | 5 per number and 20 per IP, per hour | |
| Verifications | 60 per IP per hour | |
| Session lifetime and idle timeout | 7 days absolute, 24 h idle | Conservative |
| Phone format (FQ-1) | Indian mobile only, stored as E.164 | Matches the existing sign-in copy; one module to change |
| Account creation (FQ-2) | `auto`: the first successful sign-in creates the account | `existing` mode is implemented and tested |
| Failure counter after success | Not reset | Conservative |

Values outside safe ranges are refused at startup. The two HMAC keys must differ and be at least 32 characters.

## 7. Remaining blockers and decisions
- **FQ-1 to FQ-4:** confirm or change the provisional values above.
- **FQ-2:** auto-create versus existing accounts only. In `existing` mode, the extra provider call for known numbers will cause a timing difference once a real SMS provider is used.
- **SMS provider choice and credentials:** needed before any non-development sign-in.
- **AC-14, the production proxy chain:**
  - The per-IP limit uses the right-most `X-Forwarded-For` entry from the Next.js server.
  - In production, the reverse proxy must overwrite that header.
  - Locally, a client could spoof the value.
- **R9 and R34, staff sign-in:** the admin and genealogist areas stay ungated previews until then.
- **R35 and R10:** the suspended and deleted account states.
- **Data model:** the data model and specifications remain unapproved drafts. The schema follows §5 as proposed.
- **Prisma CLI advisories:** carried over from TASK-07 (the development-only tree; the fix is 7.10.1). Not upgraded.
