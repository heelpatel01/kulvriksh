## What was implemented

### 1. Local PostgreSQL 18 (project-local, loopback only)

- **Version and source:** PostgreSQL **18.6**, from the EnterpriseDB Windows x64 binaries zip, extracted to `.data/postgres/pgsql` (git-ignored).
  - Archive SHA-256: `fbe23da234ee31547bf8a36d29dfd81e82b849df2d2b78d2eecb43d360252f8c`
  - One file is signed by EnterpriseDB Corporation; the others are unsigned, which is how EDB ships this zip.
- **Footprint:** no installer, Windows service, admin rights or global configuration.
- **Network and authentication:**
  - The cluster is in `.data/postgres/data`, with `listen_addresses = '127.0.0.1'` and `port = 5434`.
  - SCRAM-SHA-256 passwords are required for every connection (`pg_hba.conf`).
  - The other project's server on 5433 was not touched.
- **Roles** (data model §9.7):
  - `kulvriksh_owner` owns the databases and runs migrations.
  - `kulvriksh_app` is the runtime role: `SELECT`, `INSERT`, `UPDATE` and `DELETE` on application tables only. It has no DDL rights, no superuser, `CREATEDB` or `CREATEROLE`, no access to `_prisma_migrations`, and a 5-second statement timeout.
- **Databases:** `kulvriksh` (development), `kulvriksh_test` (integration tests) and `kulvriksh_shadow` (owner-only, used by `prisma migrate dev`).
- **Secrets:**
  - Passwords and the admin preview token are generated with `crypto.randomBytes`.
  - They are written only to the git-ignored `apps/api/.env`, `apps/web/.env.local` and `.data/postgres/superuser.pw`.
  - They were never printed, and never passed on a command line (SQL goes to `psql` on stdin).
- **Tool:** `scripts/local-db.mjs`, with the root scripts `db:init`, `db:start`, `db:stop`, `db:status` and `db:migrate`. It never overwrites existing files or data.

### 2. Prisma 7.10.0, pinned exactly

- **Packages:**
  - dependencies: `@prisma/client` 7.10.0, `@prisma/adapter-pg` 7.10.0, `pg` 8.23.1
  - development: `prisma` 7.10.0
- **Lockfile:** updated consistently (`f8f5b579…`).

The fix is Prisma 7.10.1, which isn't the authorised version and is younger than 14 days until 2026-10-29. The runtime packages are not affected.

### 3. API

- **Shared client:** `src/db.ts` creates one shared `PrismaClient` per process: a PostgreSQL adapter pool of 5 with a 2-second connection timeout, connecting lazily. It is wired into startup and graceful shutdown in `src/server.ts`, which disconnects after in-flight requests finish.
- **Readiness:** `/ready` now runs a real `SELECT 1`, bounded at 2 seconds. It returns `503` with database `down` when PostgreSQL is unavailable; details are logged in the safe form and never returned. `/health` is unchanged.
- **First migration:** `prisma/migrations/20261024193304_create_service`, applied to the development and test databases. It creates the `service` table (data model §6.1) with:
  - `uuid` id, `service_status` enum (`active`/`inactive`), `name`, `description` and timestamps
  - an index on status
  - CHECK constraints rejecting blank values and over-long text
- **Services feature** (`src/services/`): validation (strict, trimmed, unknown fields rejected), a repository, and routes:
  - `GET /api/v1/services` returns **active services only** (AS-PUB-07).
  - `GET`, `POST` and `PATCH /api/v1/admin/services` list, create, edit, and activate or deactivate. New services start inactive.
  - Writes must be JSON (`415` otherwise), limited to 16 KB.
  - Errors: `400 VALIDATION_FAILED` with per-field messages, `404` for unknown or malformed ids, and `503` when the database is unavailable. Codes `P1000`, `P1001`, `P1002`, `P1008`, `P1017` and `P2024` were observed or mapped.
- **Admin gate** (`src/admin-preview.ts`):
  - A development-only shared secret (`ADMIN_PREVIEW_TOKEN`) sent by the Next.js server, never by the browser.
  - It is compared in constant time.
  - Configuration refuses it outside development, so in test and production configurations every admin request is denied.
  - **It is not authentication.** It identifies no user; real admin sign-in is M4.
- **Configuration:** `ADMIN_PREVIEW_TOKEN` validation was added; the `DATABASE_URL` validation from TASK-06 is kept. The error envelope has optional `fields`, and the shared types now include `PublicService` and `AdminService`.

### 4. UI: Admin → Services (`/admin/services`)

- **Live data:** the screen reads live data from the API on the server side. **It has no sample data path.**
- **States:** it shows live rows, or an explicit "not connected", "unavailable" (with Try again) or "not authorised" state.
- **Interactions:** add service, edit, activate and deactivate, with confirmation dialogs. Field errors come back from the API's validation.
- **Writes:** Server Actions call the API server-to-server. Next.js checks the request origin, and the browser never calls the API or sees the token.
- **Plans page:** it keeps its clearly labelled sample data, because plans and prices (R12–R14) are not decided.

### Why "service" was chosen

`service` is the only catalogue entity in data model §6.1 with a *Confirmed* basis (approved scope item 3) and an existing admin flow (Product Flows F-ADM-04). The UI already displayed it, and its schema is unambiguous apart from the descriptive fields. The data model gives name and description as examples for those, and they are marked provisional here.

Plans, prices, currency and entitlements change the schema materially and are still TBC, so they were not modelled. The audit log for activation changes waits for the `audit_event` design (CP2), so a structured log line is the interim record.

## How to run locally (PowerShell)

```powershell
npm run db:start                 # PostgreSQL on 127.0.0.1:5434 (already initialised; db:stop to stop)
npm run dev:api                  # API on http://127.0.0.1:4100
$env:PORT=3105; npm run dev:web  # then open http://localhost:3105/admin/services
npm run test:db                  # database integration tests
```

On a fresh machine, first extract the PostgreSQL binaries and run `npm run db:init` (see README, "Local database").
